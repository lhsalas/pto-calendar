01Verified in the repository

The foundation is already here.

The current Express API can be the single source of truth for the browser, a CLI, and an MCP adapter. Keep validation and permissions on the server.

Evidence: PTO routes and services, calendar range/query, authorization rules.

Ready to reuse

Business rules & permissions

Shared validation covers real ISO dates, date ordering, weekday start/end, 500-character notes, and overlaps. Single-day PTO requires morning, evening, or all_day; multi-day PTO normalizes to all_day.

Missing capability

Agent-friendly authentication

requireAuth accepts cookie sessions only. The default cookie lifetime is 24 hours, configurable. There is no PAT model, bearer-token verifier, token settings page, CLI workspace, or MCP dependency.

Partially ready

Auditing & request tracing

Update/delete are audited transactionally. Create is not audited. Request IDs, sensitive-header redaction, and Redis-backed production rate limiting already exist; token identity and token-lifecycle events do not.

Important product boundary

No approvals, no team tenancy

PTO is informational; there is no approve/reject workflow or PTO status field. The schema has one shared calendar and no team-membership model. Do not invent approval tools or claim team isolation.

Integration traps to resolve before enabling writable agents
  • PUT can erase a note: an omitted note normalizes to null. A “change my end date” tool must not send a sparse PUT. Frontend UpdatePTORequest marks fields optional, but the backend still requires both dates.
  • Queries can silently truncate: take: 1000 has no pagination or completeness flag. There is no server-side userId filter. Filtering after truncation can make “my PTO” look empty or incomplete.
  • Overlap checks are not atomic: create/update check for overlap before writing. Concurrent writers can race; use a database-enforced date-range exclusion or a correctly locked/serializable transaction with retry handling.
  • No retry or concurrency contract: there is no idempotency-key handling, row version, or conditional update/delete. A timed-out write is not proof that it failed.
  • Not a drop-in frontend client: frontend/src/api/client.ts is Vite-configured and cookie-based. Types are hand-maintained in frontend/src/types/api.ts; no generation command is present. Build a runtime-neutral shared client instead of importing browser code.
  • Do not reuse setup tokens: existing account-setup tokens are single-use, short-lived password-setup credentials. Their random-secret + SHA-256 storage pattern is useful, but PATs need a separate lifecycle and table.
02Recommended approach

One API. Two ways in.

The CLI and MCP are complementary. Ship the token foundation first; put a small, typed adapter in front of the existing API for each agent environment.

Recommended · first interface

A CLI for terminal-based agents

A pto command provides predictable flags, JSON output, stable exit codes, and explicit write confirmation. Easy to script and useful without an AI agent.

Best fit: agents that can execute local commands. No new public service or protocol endpoint.

Recommended · same foundation

A local stdio MCP server

A local process exposes typed PTO tools to an MCP-capable agent. It loads the user’s API token from a credential store or process environment, then calls REST over HTTPS.

Best fit: clients that can launch local MCP processes. No repeated browser login for tool calls.

Suggested workspaces: packages/api-client for runtime-neutral requests/contracts, cli for command parsing and output, and mcp for tool definitions. Both adapters call REST directly; neither bypasses the API or shells out to the other.

When a hosted HTTP MCP endpoint is worth the extra work

Use hosted Streamable HTTP MCP if the selected clients cannot launch local processes, or if centrally hosted agents need remote access. First verify each target client’s supported transport and authentication mode.

  • A PAT-protected REST API is not automatically an MCP server. HTTP MCP adds protocol lifecycle, tools, transport behavior, and its own authentication boundary.
  • The current MCP HTTP authorization framework is OAuth-based and implementations SHOULD follow it. For broad compatibility, plan protected-resource metadata/discovery, authorization-server integration, PKCE-capable flows, resource/audience validation, scopes, and refresh-token management.
  • Custom static-bearer authentication can work with explicitly compatible clients; do not advertise universal compatibility. A UI-created REST PAT is not a substitute for OAuth discovery.
  • A remote MCP server must only accept tokens intended for itself. Do not forward an inbound MCP token to a separate upstream API. Co-locate and call the domain layer under a verified principal, or obtain separately authorized upstream credentials.
  • Add reverse-proxy routing for /mcp and OAuth metadata/authorization paths; verify streaming/buffering, timeouts, HTTPS, Origin validation, and multi-client isolation.
  • If OAuth is chosen, keep access tokens short-lived. A rotating, revocable refresh grant can provide the convenient login experience, but cap the absolute grant lifetime at 365 days if the same one-year policy applies. This is a different design from a one-year PAT.

Protocol guidance: MCP authorization and token audience / passthrough rules, verified via Context7.

03Required security foundation

Long-lived, not all-powerful.

Give every member, team lead, and admin self-service personal access tokens. A token acts as its owner; it never creates a new role or grants more access than that person has.

Lifetime
Offer 30 / 90 / 180 / 365 days, with 90 days recommended by default. Enforce 0 < expiresAt − createdAt ≤ 365 × 24h on the server in UTC. No “never expires,” sliding extension, or configuration override above the cap. Reject at now ≥ expiresAt.
Creation & visibility
Only an authenticated browser session may mint a token, for that same user, after recent password verification. Return the raw secret once with Cache-Control: no-store. Later list/detail responses contain metadata only.
Secret format & storage
Use an opaque token such as pto_pat_<public-id>.<random-secret>, with at least 32 cryptographically random bytes of secret. Store only a SHA-256 digest of the secret and a non-secret display prefix. High entropy makes a fast digest appropriate; do not store plaintext or encrypt tokens just to reveal them later.
Validation on every call
Parse the bearer header strictly, look up the public ID, compare the digest safely, and check expiry, revocation, owner existence/account eligibility, credential version, and live role. Fail closed on database errors. Convenience removes repeated interactive sign-in, not request authentication.
Revocation & resets
Revoke one or all of your tokens immediately for subsequent requests. Bind issuance to the owner’s sessionVersion; password reset/setup already increments it and should invalidate existing PATs too. Deny PATs while passwordHash is null. Ordinary browser logout does not revoke PATs.
Least privilege
Default to read-only. Users explicitly opt into create/update/delete capabilities. Team-level scopes require a current lead/admin role at issuance and use. Revoke elevated tokens on demotion so a later promotion cannot accidentally resurrect their privileges.
Client-side protection
Use the OS credential store where available, otherwise an explicitly accepted owner-only file. Environment injection is a noninteractive fallback, not a secret vault. Never put tokens in command arguments, URLs, repository files, frontend build variables, browser localStorage, prompts, or tool results.
Renewal
Warn before expiry and let users create a replacement in the UI. Allow a brief user-controlled overlap, then revoke the old token. No automatic extension of an existing PAT; each replacement has its own hard expiry and recent-auth check.

Why opaque PATs instead of one-year JWTs? This application already uses PostgreSQL-backed user checks. A stored token record gives simple immediate revocation, per-device visibility, and up-to-date permissions without adding a JWT refresh/blocklist subsystem.

Add a dedicated PersonalAccessToken model and migration; do not change cookie lifetime or overload setupTokenHash.

These PATs grant no user administration, password reset, holiday administration, audit browsing, or token-minting access. Apply a bearer-route allowlist so broadening requireAuth does not accidentally open every existing route.

Authentication and CSRF integration requirements
  • Introduce an auth context with method: session | pat, actor, token ID, scopes, and request ID. Keep session-specific fields out of the shared actor type.
  • Make credential choice unambiguous. Reject requests carrying both session and bearer credentials; an invalid bearer must never fall back to a valid cookie.
  • Keep token management session-only. An otherwise valid PAT must not list, mint, revoke, or reset credentials, nor log into a browser session.
  • The current CSRF middleware runs before route authentication. Refactor ordering/policy deliberately: exempt only successfully verified, cookie-free bearer requests from cookie-specific CSRF requirements. Do not bypass checks merely because an Authorization header exists. Preserve rejection of disallowed browser origins.
  • Keep existing cookie protections and regression tests. Native CLI/stdio requests are not subject to browser CORS; there is no need to loosen CORS to *.
  • PAT validation must use current permissions. Existing session role caching defaults to 15 seconds; do not copy that cache into a path promising immediate role/revocation enforcement.
  • The schema has no disabled-user flag. Version invalidation and password-reset blocking cover existing flows; introduce an account-status field only if a separate suspension/offboarding feature is added.

Write safety, response contracts, and deployment details
  • Versions: add PTORequest.version (integer, default 1). Return it on reads/writes. Update/delete atomically require the expected version through a documented precondition. Approved proposal update (15 Nov): missing precondition returns HTTP 428; failed If-Match returns HTTP 412 STALE_WRITE, not the original illustrative 409. Reserve 409 for business/idempotency conflicts. Apply the rule consistently to browser and PAT writes, including legacy PUT.
  • Idempotent create: support Idempotency-Key and store a request fingerprint + result scoped to actor, token, and operation. Same key/payload returns the original result; same key/different payload conflicts. Do not use the key as a substitute for authentication. Define a retention window and do not retry beyond it without reconciliation.
  • Overlap integrity: enforce no overlapping inclusive date ranges for the same owner under concurrent requests. Preserve the current rule that even different half-day entries on the same date conflict.
  • Errors: retain { error: { code, message, details? } }, HTTP 400/401/403/404/409/412/428/429, Retry-After, and X-Request-Id. Use a generic credential failure for unknown/expired/revoked PATs; never echo the supplied secret.
  • Privacy: keep list notes redacted. Redact detail and mutation responses unless both note scope and existing note authorization permit disclosure; do not let a read token enumerate privileged notes.
  • Contract maintenance: add bearer security as an alternative to cookies on PTO routes in docs/openapi.yaml; explicitly retain cookie-only token management. Align frontend types and introduce generated or contract-tested shared types.
  • Deployment: existing nginx /auth and /pto proxies already cover the proposed local-client REST paths. Verify Authorization forwarding, no-store behavior, trusted proxy settings, and TLS in the deployed chain; no new public port is needed.

06Writable agents need guardrails

A token is permission.
Not consent.

The API must enforce authority even when an agent is mistaken. The agent client must separately establish that the user actually wants a particular change.

  • SAFE-01 · ConsentShow the exact user, dates, day part, and update diff or delete target before writes. Require confirmation for create/update/delete in supported agent hosts. Tool annotations and a model-supplied confirmed: true are hints, not proof of human approval; if server-enforced approval is mandatory, add a separately authenticated approval flow.
  • SAFE-02 · Correct datesUse ISO date-only fields; resolve “next Friday” in the user’s intended timezone and confirm the absolute date. Never silently shift weekend dates or treat evening as a new enum value like afternoon. Display the existing PM meaning clearly.
  • SAFE-03 · Private contextPTO notes can contain sensitive personal information. Default notes off for agent access; opt in only when needed and authorized. Explain that data returned to a cloud AI agent may leave the app’s hosting boundary, and apply the organization’s retention/model policy.
  • SAFE-04 · Prompt injectionTreat names, notes, and all tool results as untrusted data—not instructions to run commands, reveal credentials, or change another record. Do not let tool inputs choose arbitrary URLs, file paths, shell fragments, or headers.
  • SAFE-05 · Safe networkingBind credentials to a configured, trusted HTTPS origin. Permit plain HTTP only for explicit loopback development. Reject cross-origin credential redirects, validate TLS, use real request cancellation/timeouts, and never log Authorization headers or token bodies.
  • SAFE-06 · Retries & concurrencyRetry bounded reads with backoff and respect Retry-After. Retry create only with the same persisted idempotency key. On stale version, read again and ask before overwriting. Reconcile an ambiguous write rather than claiming it failed or blindly repeating it.
  • SAFE-07 · Abuse controlsKeep the shared Redis-backed IP limiter and add verified-token/user limits so office NATs do not make every agent share one quota. Rate-limit invalid bearer attempts and token issuance separately. No uncontrolled polling or unbounded agent loops.
  • SAFE-08 · AccountabilityAudit create/update/delete and token creation/revocation with actor, token ID, target owner/record, request ID, and credential type. Never store the raw token in audit details. Preserve transactionality and define note/audit retention; existing update audits currently include the note text.

Rollout rule: start with read-only tokens. Enable personal writes only after scope enforcement, note privacy, safe updates, retry protection, concurrency handling, and audit coverage pass. Team-wide writes are a separate explicit opt-in.

08Recommended defaults & open choices

A few decisions before coding.

These are the original assessment questions. The 15 November addendum and approved contract record the selected clients, frozen token policy, explicit scopes and host-consent boundary. Concrete protocol/SDK/client versions and configuration recipes still require actual testing; follow current official client docs rather than freeze unverified snippets.

  • Which agent clients will people use?Confirm whether they can execute a CLI, launch local stdio MCP, or only connect to hosted HTTP MCP. This determines the adapter priority.
  • What is the token policy?Recommended: 90-day default, hard 365-day maximum, 10 active tokens per person, recent password verification, and no PAT renewal endpoint.
  • Who can delegate team-wide writes?Recommended: all users may manage their own PTO; lead/admin team scopes require explicit selection. No blanket “act as admin” token.
  • Should the agent see private notes?Recommended: off by default, explicit scope, existing owner/lead authorization, and an approved AI-provider data policy.
  • How strong must approval be?Recommended: trusted host confirmations and read-only-by-default tokens. If server-enforced human consent is required, budget a distinct approval mechanism.
  • Is create-on-behalf required?Not needed for the requested personal CRUD workflow. Supporting it requires a new owner-selection contract and explicit permission/audit rules; do not sneak it into this change.

Bottom line: yes, this project can support the requested experience without replacing its authentication or PTO domain. Add self-service PATs and scoped bearer access, harden automated writes, then expose the same API through a CLI and local MCP server.
